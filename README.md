# Saans

Saans is a GenAI urban air-quality assistant. It checks today's air where you live, then generates a household plan for smog and everyday air pollution: a low-emission daily routine, indoor air-quality hacks, sustainable alternatives, community actions and a clear estimate of what each choice changes.

The plan is written by a language model at request time from live air data and the answers you give. There are no canned plans and no sample advice in the code.

## What Saans does

1. **Find your air.** Search for a city or use your location. Saans reads Open-Meteo air quality and weather data for those coordinates and shows the current PM2.5, US AQI, a plain-language category, the cleanest and worst hours, and a short trend.
2. **Describe your household.** Choose household members, how you travel, your home type, cooking fuel, heating, budget, plan language and reading mode. The optional note is limited to 200 characters.
3. **Get a plan.** The live air card is headed **Today's air**. Below it, the model's air summary and sections render under **Your plan**, **Low-emission daily routine**, **Indoor air quality hacks**, **Sustainable alternatives**, **Your impact** and **What families and communities can do**.
4. **See the impact.** The model chooses impact factors by ID; the code looks up the numbers. Each impact is labelled as an estimate with its source.
5. **Try what-if choices.** Select or clear exposure measures and see the estimated change in daily PM2.5 exposure and avoided trip emissions.
6. **Ask a follow-up.** Ask Saans answers one question about the current plan, in the chosen language, with the same air digest and plan as context.
7. **Use it your way.** Print the plan, read it aloud where the browser supports speech synthesis, or switch to simple reading mode. Plans are available in English, Hindi and Bengali.

Saans is not medical advice. A not-medical-advice note sits beside the plan, and the prompt requires a talk-to-a-doctor line for sensitive groups at poor air quality.

## Architecture

### Request flow

1. The browser loads `/`. `src/app/layout.tsx` renders the header, skip link, main landmark and data attribution; `src/app/page.tsx` renders the client shell `SaansApp`.
2. A place search calls `GET /api/geocode?q=…`. The route validates the query with Zod, rate-limits the request, then calls Open-Meteo geocoding through the allowlisted HTTPS fetch wrapper.
3. Selecting a place calls `GET /api/air?lat=…&lon=…&name=…`. `getAirDigest` fetches air quality and weather in parallel, rounds coordinates to two decimals, caches upstream responses for ten minutes and analyses the hourly series into a small digest.
4. Submitting the profile calls `POST /api/plan`. The guard rate-limits and validates the body, rebuilds the digest, creates the ordered LLM client and calls `generatePlan`.
5. `generatePlan` builds a prompt containing the digest, profile and factor catalog, requests strict JSON, validates it with Zod, retries once with a validation summary, then replaces factor IDs with catalog factors and computed estimates.
6. The UI renders the plan, impact badges, what-if panel, print and read-aloud tools. `POST /api/ask` answers follow-up questions with the same digest and plan, validated against the ask schema.
7. `GET /api/health` reports whether each LLM client is configured; `?probe=1` makes one tiny live call per configured client.

## How the AI is used

- **Prompting.** The system prompt sets the role, safety rules, language and reading mode. The user prompt contains the air digest, the profile, the factor catalog (IDs and labels only) and the required JSON shape. Free text is sanitised, limited to 200 characters and wrapped in `<user_note>` tags; follow-up questions are wrapped in `<question>` tags. The prompt tells the model to treat both as data, not instructions.
- **Structured output.** The plan and answer schemas are strict Zod objects. A reply that is not valid JSON or does not match the schema is sent back once with a short validation summary (never the raw reply), and the model is asked for corrected JSON only. A second failure returns a safe `LLM_BAD_OUTPUT` error.
- **The model chooses; the code supplies numbers.** The model returns `factorIds`, never percentages or kilograms. `src/lib/impact/estimate.ts` looks each ID up in `src/lib/impact/impact-factors.ts` and computes the estimate. Unknown IDs are dropped. This keeps every impact number traceable to the catalog.
- **Provider fallback.** `createLlmClient` builds an ordered list: the primary Gemini model, a second Gemini model, then OpenRouter when both its key and model are set. `FallbackLlmClient` tries each in turn and fails only when all fail. Model IDs live only as defaults in `src/lib/config.ts` and as optional values in `.env.example`.
- **Limits.** Plan output is capped at 4,096 tokens, answers at 1,024, temperature is 0.4 and each model call has a 25-second timeout. The plan and ask routes export `maxDuration = 30` so Vercel does not cut the call short.
- **No canned advice.** On any LLM failure the UI shows a clear error and a retry button. It does not substitute a sample plan.

## Impact model and its limits

The catalog has 14 factors: nine exposure factors (masks, air cleaners, ventilation, cooking and timing) and five lifestyle factors (walking or cycling, public transport, carpooling, avoiding open burning and wet mopping).

- **Exposure estimate.** The baseline combines the daily mean PM2.5 with the hours typically spent outdoors for the chosen commute and an indoor infiltration factor of 0.7. Each selected exposure factor reduces the relevant outdoor or indoor part. Factors in the same group (for example two masks) count once, using the strongest selected choice.
- **Trip emissions.** Walking, cycling, public transport and carpooling show avoided kg CO2e per 10 km trip compared with driving alone.
- **Timing.** Moving outdoor activity is computed from today's cleanest forecast window rather than a fixed percentage.

Every impact number is an **estimate**, not a measurement. The ranges are approximate round numbers based on public-health and vehicle-emission guidance, and the source for each factor is shown in the UI. The model does not model dispersion, building air exchange, activity level, age or health status. It is not a substitute for a local air-quality monitor or medical advice. The what-if panel is a planning aid, not a prediction.

| Service | Used for | Where |

| Open-Meteo Air Quality API | PM2.5 and hourly air forecast | `https://air-quality-api.open-meteo.com` via `src/lib/air/clients.ts` |

| Vercel | Hosting and serverless functions | Deployment only; no SDK in the code |

Only those hosts are allowlisted in `src/lib/config.ts`. Every outbound request uses HTTPS, an `AbortSignal` timeout and the shared safe-fetch wrapper.

## Security measures

- **Validation at every boundary.** Request bodies and query strings, upstream API responses and LLM output are parsed with Zod. Invalid input gets a safe `VALIDATION_FAILED` response.
- **Secrets.** API keys are read only in `src/lib/config.ts` from `process.env`, never exposed to client code, never logged and never committed. `.env.example` holds placeholders only.
- **Health data stays in memory.** Profile answers are held in React state and sent in the request body. They are not stored in a database, not written to logs and not put in URLs.
- **Free text.** At most 200 characters, control characters and angle brackets stripped, whitespace collapsed, and placed inside `<user_note>` tags with an instruction to treat it as data.
- **Outbound requests.** Host allowlist, HTTPS only and an `AbortSignal` timeout on every call.
- **Rate limiting.** Every `/api` route allows 20 requests per IP per minute and returns `429` with `Retry-After`. The limiter is in memory and resets per serverless instance; it blocks bursts but is not a shared quota.
- **Headers.** A CSP, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` and `poweredByHeader: false`.
- **Rendering.** LLM text is rendered as React text nodes. There is no `dangerouslySetInnerHTML` and no `eval`.
- **Errors.** A typed `AppError` carries a stable code and a safe message. Stack traces and upstream details are never sent to the browser.

## Accessibility statement

Saans aims to meet WCAG 2.2 AA.

- The layout has a header, one main landmark, a footer and a skip-to-content link. Each page has one `h1` and headings in order.
- Every input has a visible label. Groups use `fieldset` and `legend`. Errors use `aria-describedby` and `role="alert"`, and the error summary moves focus to the first problem.
- Results and loading states are announced with `aria-live="polite"`. When a plan arrives, focus moves to its heading.
- AQI is never shown by colour alone: every level has a text label and an icon or shape, and colours target AA contrast.
- The interface is keyboard operable with a visible focus ring, and primary controls use touch targets of at least 44px.
- Motion respects `prefers-reduced-motion`. Type is sized in `rem`.
- The plan container carries the chosen language, so screen readers switch voice. Simple reading mode shortens the language, and a read-aloud button uses the browser's speech synthesis when available.
- Page-level components and the plan view have automated vitest-axe checks.

## Deployment on Vercel

1. Push the repository to GitHub and import it in Vercel as a Next.js project.
2. Add `GEMINI_API_KEY` in **Project → Settings → Environment Variables**. Add `OPENROUTER_API_KEY` and `OPENROUTER_MODEL` only if you want the fallback provider. Model names are optional; the defaults are in `src/lib/config.ts`.
3. Never commit `.env.local` or paste a key into the repository. Environment variables belong in the Vercel dashboard.
4. Deploy. The plan and ask routes allow up to 30 seconds (`maxDuration = 30`).
5. Open `/api/health?probe=1` on the deployed URL. Gemini should report `ok`.

The in-memory rate limiter resets when a serverless instance is replaced. That is acceptable for burst protection but not for a shared production quota; a Redis or Upstash-backed limiter is the future fix.

## Limitations and future work

- **LLM free tiers can be slow or rate-limited during grading.** The second Gemini model and the optional OpenRouter provider exist for this. Without any configured provider the app shows a clear error instead of a plan.
- **The rate limiter is per instance.** A shared store would make limits consistent across serverless instances.
- **Impact factors are approximate.** They are round planning numbers, not measurements or a dispersion model. A future version could use local monitor data and a validated exposure model.
- **Air data is model-based.** Open-Meteo and CAMS ENSEMBLE provide forecast and reanalysis data, not a sensor on your street.
- **No accounts or saved plans.** Health-related profile answers stay in memory by design. Persistence would need a privacy review.
- **Read-aloud depends on the browser.** The button is hidden when speech synthesis is unavailable.
- **Languages.** English, Hindi and Bengali are supported. More languages need prompt and UI review, not just a new label.
- **No push alerts or notifications.** Saans is a check-today tool, not a monitoring service.
